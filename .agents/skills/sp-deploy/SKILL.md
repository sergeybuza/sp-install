# Развёртывание Смарт Платформы

Работай из проекта `sp-install` и соблюдай его `AGENTS.md`. Скилл описывает процедуру, но не предоставляет сетевых разрешений, доступа к секретам или права удалять существующие данные. Учитывай разрешения текущей задачи и не запрашивай их повторно.

## Выбор процедуры и доступ

Прочитай инвентарь целевого ПК в `inventory/hosts/`, [инвентарь поставки](../../../inventory/releases/smart-platform-2.0.0.md), [подготовку Docker](../../../docs/installation/ubuntu-26-docker.md) и [инструкцию платформы](../../../docs/installation/smart-platform-2.0.0.md). Исторический результат не подтверждает текущее состояние стенда. Команды ThingsBoard не заменяют подтверждённые команды этого форка.

Определи узел, SSH-пользователя, разрешённые адреса репозиториев и способ аутентификации. Секреты получай из окружения, для стенда — `SP_STAND_PASSWORD`. Не ищи пароль в истории чатов, shell history, `.env` или пользовательских SSH-файлах. При отсутствии аутентификации выполни независимую локальную подготовку и сообщи, что удалённая часть не начата.

Инструкция требует единственный закрытый MQTT-ключ `/opt/smart-platform/certs/server.key`, `0600`, UID/GID `100:101`. Используй это исключение только при разрешении владельца в текущей задаче. Остальные секреты передавай через окружение; не сохраняй их в файлы и аргументы команд. Не печатай полный Compose config, Docker inspect, ответы API, токены устройств или сырой вывод установщика без проверки на секреты.

## Проверка перед установкой

На целевом ПК проверь SSH/sudo, ОС и архитектуру, CPU, память, место на диске, состояние пакетов, занятые порты и существующие ресурсы Docker. Конфигурация проекта проверена на Ubuntu 26.04.1 / amd64 с 4 CPU и 14 GiB RAM; это описание проверенного окружения, а не установленные минимальные требования.

Различай три случая:

- Новая установка: нет каталога установки, контейнеров платформы и тома `sp-postgres-data`; можно выполнять первичную инициализацию.
- Существующая установка: подтверди Compose labels проекта `smart-platform`, привязку PostgreSQL к `sp-postgres-data`, конфигурацию runtime и состояние схемы. Наличие тома и неработающий UI сами по себе не определяют завершённость установки. Для подтверждённой установленной БД не запускай `sp-install`, не меняй пароль и не перевыпускай ключ. Используй раздел перезапуска инструкции, восстанавливая пароль из окружения единственного PostgreSQL-контейнера проекта без вывода.
- Частичная установка или неизвестные ресурсы: выясни состояние до следующего изменяющего шага. Не удаляй тома и каталоги, чтобы искусственно получить чистый стенд; сброс — отдельная задача.

При отсутствии Docker проверь настроенные источники Ubuntu и симуляцию установки. Для подтверждённого варианта используются `docker.io` и `docker-compose-v2`, через sudo. Установка не требует `apt upgrade`, `autoremove`, изменения сети или добавления пользователя в группу docker. После установки проверь daemon, Compose и фактические версии. При существующих чужих контейнерах сначала оцени влияние изменения пакетов.

## Новая установка

Выполняй этапы инструкции последовательно; ошибка останавливает зависимые шаги. Рабочая машина и целевой ПК — разные узлы.

Если передаёшь Bash-сценарий по SSH через stdin, у команд `docker compose exec -T ... -c ...` закрывай stdin через `</dev/null`: иначе Docker CLI может прочитать последующие строки сценария. Для намеренной передачи данных, например импорта truststore, сохраняй предусмотренный инструкцией канал ввода.

1. Сверь локальный архив `input/images/sp-images-2.0.0.tar`, CA и конфигурацию. Передай поставку в `/home/engineer/sp-install-input`, повтори сверку на стенде и установи файлы в `/opt/smart-platform`. Оригиналы `input/` не редактируй.
2. Загрузи vendor-образы из архива и сверь все четыре Image ID и архитектуры с инвентарём. Для монолита запускаются только `sp-node` и `sp-web-ui`. Загрузи PostgreSQL и Mosquitto через разрешённый Docker Hub и сверь digest. При отличии остановись и проверь изменение поставки. Не обращайся к vendor-реестру только из-за его имени в теге.
3. Подготовь truststore из стандартных CA образа с добавлением Andromeda CA. Не путай SHA-256 файла CA с fingerprint сертификата. Проверь публичные сертификаты. Выпусти MQTT-ключ только при его отсутствии и согласованном исключении; не создавай его локальную копию.
4. Используй проект Compose `smart-platform` и `/opt/smart-platform/compose/monolith.yml`. Сгенерируй пароль БД в окружение, проверь `config --quiet` и подними PostgreSQL/Mosquitto. До установщика проверь схему `smartplatform`, её владельца и нулевое число таблиц. При непустой схеме установщик не запускай.
5. Однократно выполни `checks/install-database.py` из установки: скрипт `scripts/remote/install-database.py` передают туда вместе с проверками. Он повторно проверяет пустую схему, запускает `sp-install` с профилем `install`, захватывает stdout/stderr только в память и сообщает код и наличие маркера `Installation finished successfully!`. Нужны код `0` и маркер успеха. `LOAD_DEMO=true` в текущем Compose создаёт демоданные. Не повторяй установщик после ошибки или тайм-аута без разбора контейнеров и состояния БД.
6. Подними четыре runtime-сервиса через `up --wait`: PostgreSQL, Mosquitto, `sp-back-monolith`, `sp-web-ui`. `pull_policy: never` требует заранее загруженных образов. Полезные порты, тома и назначение сервисов приведены в инструкции.

## Приёмка и результат

Проверь состояния контейнеров и healthcheck. TCP-healthcheck ядра не подтверждает API. У UI запрос `/login` требует `Accept: text/html`; без него результат не подтверждает работоспособность SPA.

На стенде запусти `platform-seed-smoke.py` из `checks/` установки: он проверяет HTML, локальные ресурсы, вход и роль `SYS_ADMIN`. Скрипту нужен соседний `platform-http.py`. Начальный пароль берётся из JAR только в память и окружение; после смены пароля нужен актуальный `SP_ADMIN_PASSWORD`. Ошибка входа не разрешает сброс пароля или повторную инициализацию.

Для MQTT TLS проверь доверие публичному `server.crt` и SAN адреса стенда на `8883`. Если проверяешь MQTT CONNECT, получай demo access token только в память и не печатай; `CONNACK 0` подтверждает подключение, но не доставку телеметрии.

Проверь штатные `stop` и `up --wait` без переустановки: перед этим зафиксируй количества контрольных сущностей БД, затем повтори сравнение и UI/API-проверку. Пароль БД восстанавливай из окружения существующего PostgreSQL-контейнера без вывода. Не используй `down -v` или удаление контейнеров для проверки перезапуска.

Сохрани в `reports/` локальный отчёт с узлом, временем и зоной, версиями, хешами, выполненными этапами, кодами завершения и границами проверок. Перенеси подтверждённые выводы в инвентарь и документацию обычным текстом, без секретов и сырых данных платформы. Отдельно укажи, выполнялись ли браузерный вход, перезагрузка ПК и промышленные сценарии; успешные smoke-проверки их не подтверждают.

Файлы проекта меняй в тематической ветке от актуальной `origin/main`, проверь состав изменений и Gitleaks после staging перед каждым коммитом. Передай PR в `main` без слияния. Ссылка на UI и описание оставшихся проверок должны быть в результате задачи.
