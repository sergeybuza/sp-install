# Инструкции для агентов

## Начало работы

- Перед началом задачи прочитай [README.md](README.md): там находятся назначение проекта, структура каталогов и ссылки на документацию. Этот файл содержит правила работы агента.
- Перед работой со стендом прочитай [справочник стендов](inventory/hosts/README.md) и карточку выбранного узла. Адреса, окружение и последнее зафиксированное состояние веди в карточках; в `AGENTS.md` и корневом `README.md` оставляй ссылки на них.
- Общайся и веди документацию на русском языке, если пользователь не попросил иначе.

## Доступ к GitHub проекта

- По явному указанию владельца от 2026-11-14 для задач этого проекта постоянно разрешены обычные операции с репозиторием `https://github.com/sergeybuza/sp-install` и его GitHub API (REST и GraphQL в рамках этого репозитория): чтение, `fetch`, отправка тематических веток, создание и обновление PR, чтение статусов проверок.
- Это исключение из личного правила о доступе за пределы папки проекта; повторно запрашивать разрешение на перечисленные операции не нужно. Оно действует и в следующих задачах этого проекта. Доступ к другим репозиториям, адресам и внешним файлам этим исключением не разрешён.
- Порядок работы с ветками и слиянием определён ниже. Если среда требует отдельного технического разрешения, запроси его.

## Оформление файлов

- Служебные метки достоверности и источника утверждений используй только в чате с пользователем. Не вставляй их в файлы проекта, включая инструкции, документацию, отчёты и комментарии к коду.
- В файлах описывай источники, основания и границы выполненных проверок обычным текстом.

## Изменения через Pull Request

- Все изменения проекта, включая документацию, конфигурацию и этот файл, вноси через Pull Request (PR) в `main`.
- Для каждой задачи создавай отдельную тематическую ветку от актуальной `origin/main` до внесения изменений.
- Не коммить и не отправляй изменения напрямую в `main`.
- Перед созданием PR проверь состав изменений и выполни применимые проверки. В описании PR укажи, что изменено, зачем, какие проверки выполнены и какие не выполнялись. Передай пользователю ссылку на PR для проверки.
- Не сливай PR и не включай автоматическое слияние без явной команды пользователя. Готовность изменений не означает разрешение на слияние.

## Gitleaks перед каждым коммитом

- После добавления изменений в индекс и до каждого коммита обязательно запускай из корня проекта `gitleaks git --pre-commit --staged --redact --no-banner .`.
- Коммит разрешён только после успешной проверки с кодом завершения `0`. Если Gitleaks недоступен, завершился ошибкой или обнаружил секреты, не создавай коммит и сообщи о проблеме.
- Если после проверки изменился состав или содержимое индексированных файлов, повтори проверку перед коммитом.
- Не отключай правила и не добавляй исключения ради прохождения проверки. В описании PR указывай результат Gitleaks.

## Секреты только в переменных окружения

- Все секреты, включая пароли, токены и закрытые ключи, храни и передавай только через переменные окружения; конфигурация и скрипты должны получать их из окружения при запуске.
- Не сохраняй значения секретов в файлах, включая исходники, Compose, конфигурацию, документацию, отчёты и `.env`, даже если файл исключён из Git.
- По подтверждённому разрешению владельца от 2026-11-12 в `docs/installation/smart-platform-2.0.0.md` допускаются только два переданных им дефолтных пароля поставки 2.0.0 для `PASSWORD_LOCAL` и `SYSADMIN_PASSWORD_LOCAL`. Все остальные значения и файлы подчиняются общему правилу хранения секретов.
- Публичные шаблоны окружения называй `.env.example`. В шаблонах допускаются только имена переменных с пустыми значениями или явно фиктивные примеры без настоящих секретов.
- Не выводи секреты в логи и ответы, не передавай их аргументами командной строки и не записывай в историю shell. `.gitignore` не заменяет эти правила и проверку Gitleaks.

## Правила работы с платформой

- Не считай поведение, конфигурацию, API, схему данных и процедуры ThingsBoard совместимыми с этим форком без подтверждения по материалам поставки или результатам проверки.
- Размещай материалы по структуре из `README.md`. Оригиналы поставки не редактируй; замечания к ним и согласованные проверенные инструкции веди отдельно. Утверждение в руководстве поставщика само по себе не подтверждает работоспособность.
- Для замечания к документу указывай исходный файл, версию при наличии, раздел или страницу, проблему и основание для исправления. Непроверенные утверждения явно помечай.
- До подготовки исполняемой установки выясни версии Ubuntu, Docker и Compose, архитектуру ПК и образов, состав сервисов, теги или дайджесты, порты, тома, зависимости и необходимые ресурсы. Не подставляй вымышленные значения.
- До запуска скриптов и команд проверяй, какие пути, данные и сервисы они затрагивают. Подготовка файлов для целевого ПК не разрешает менять настройки текущего компьютера.
- Разделяй скрипты по месту выполнения согласно структуре из `README.md`. В инструкциях явно указывай место выполнения команды и целевой узел.
- Результаты отдельных запусков сохраняй локально в `reports/` с указанием ПК и времени запуска. Подтверждённые выводы переноси в документацию без секретов и рабочих данных.
- Не добавляй в Git архивы образов, рабочие данные платформы, логи и резервные копии. Перед коммитом проверяй состав изменений, материалы на секреты и персональные данные; соблюдай правила работы с секретами выше.
- Записывай фактически выполненные проверки, окружение и их результаты. Проверка на машине разработки не подтверждает установку на целевом промышленном ПК.
