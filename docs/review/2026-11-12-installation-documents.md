# Замечания к документам установки Смарт Платформы

Дата проверки: 2026-11-12. Замечания относятся к локальному развёртыванию на стенде `192.168.10.107`. Оригиналы документов сохранены без изменений.

Источники:

- `input/docs/Инструкция по развороту СП rev.01.docx` — далее «короткая инструкция», версия `rev.01` указана в имени файла. Ссылки даны по разделам: номера страниц в оглавлении и колонтитулах расходятся.
- `input/docs/РП. Смарт Платформа.pdf` — далее «руководство», 500 страниц; номер релиза платформы не установлен. Дата создания в метаданных — 2026-10-01. Номера страниц ниже соответствуют страницам PDF.

**Граница проверки.** [ПРОВЕРЕНО] Короткая инструкция прочитана полностью и просмотрена после рендеринга всех восьми страниц. В руководстве выполнен тематический поиск по 500 страницам, прочитаны установочные разделы на с.455–458 и 465–468; с.455 также проверена визуально. Это подтверждает содержание документов, но не работоспособность описанных ими команд. Стендовые сведения ниже приведены отдельно от результатов чтения документов.

## 1. Пакет Compose зависит от выбранного репозитория

**Источник:** короткая инструкция, раздел 3.2, шаг 1: `sudo apt install -y docker.io docker-compose-plugin`.

**Проблема:** команда не соответствует пакетам штатных репозиториев проверяемого стенда: `docker-compose-plugin` там не найден, установленный Compose поставляется пакетом `docker-compose-v2`.

**Основание:** [ПРОВЕРЕНО] В локальном отчёте `reports/stand-192.168.10.107-20261112T105906Z-environment.md` зафиксированы Ubuntu `26.04.1`, `docker.io` версии `29.1.3-0ubuntu4.1` и `docker-compose-v2` версии `2.40.3+ds1-0ubuntu1`. `apt-cache show docker-compose-plugin` завершился с кодом 100 и `E: No packages found`. Журнал APT содержит успешную транзакцию `apt install -y docker.io docker-compose-v2` от 2026-11-12; журнал sudo — предшествующие вызовы установки с `docker-compose-plugin`, но не их результаты. `apt-get -s install docker.io docker-compose-v2` завершился с кодом 0: оба пакета уже установлены, изменений нет. История shell не содержит нужных команд; последовательность восстановлена по журналам sudo и APT.

**Исправление:** для процедуры со штатными пакетами этого стенда указывать `docker.io` и `docker-compose-v2`. Установку из репозитория Docker описывать отдельным вариантом, если он будет выбран и проверен. Предварительные шаги и последовательность команд в инструкции сопровождать источниками: журналы, установленные пакеты и настроенные источники APT.

**Состояние:** исправление имени пакета подтверждено для репозиториев и окружения данного стенда. Чистая установка Docker в текущей проверке не повторялась; выполнена симуляция установки уже присутствующих пакетов.

## 2. Пример Compose не определяет фактическую поставку

**Источник:** короткая инструкция, разделы 2.3, 3.3 и 3.5.

**Проблема:** указаны `sp-core:<укажите_тег>` и `sp-web-ui:<укажите_тег>`, а для PostgreSQL — только `postgres:15`. Нет идентификатора релиза, дайджестов, контрольных сумм архивов и паспорта конфигурации. Сам документ требует уточнить имена переменных и пути сертификатов по спецификации релиза.

**Основание:** [ПРОВЕРЕНО по документу] В разделе 2.3 предлагается запросить образы и сопроводительные материалы у поддержки; адреса скачивания и точные теги в документе отсутствуют. [ПРОВЕРЕНО] В `input/images/` присутствует только README; по локальному отчёту проверки стенда список Docker images пуст, поиск архивов и Compose в `/home`, `/root`, `/opt`, `/srv`, `/mnt`, `/media` совпадений не дал. Этот поиск не охватывает все возможные имена и пути файлов.

**Исправление:** получить поставку; зафиксировать происхождение, теги или дайджесты, архитектуры, контрольные суммы архивов и спецификацию конфигурации в `inventory/releases/`. Проверить конфигурацию и entrypoint полученных образов до подготовки исполняемого Compose. Значения вместо шаблонов не подставлять предположительно.

**Состояние:** неполнота документа подтверждена. Получены и загружены четыре [образа 2.0.0](../../inventory/releases/smart-platform-2.0.0.md), затем оригинальный `docker-compose_monolith.yml`. На его основе развёрнут монолит с PostgreSQL16 и Mosquitto2; ID, архитектуры и контрольные суммы поставки проверены. Отдельные JS/MQTT из архива не требуются выбранному монолитному составу.

## 3. Хранение пароля в файле противоречит правилам проекта

**Источник:** короткая инструкция, раздел 3.5, шаг 2 и пример `env_file: .env`.

**Проблема:** документ предлагает сохранить пароль PostgreSQL в `.env`.

**Основание:** [ПРОВЕРЕНО] `AGENTS.md`, раздел «Секреты только в переменных окружения», запрещает сохранять значения секретов в файлах, включая игнорируемые `.env`.

**Исправление:** получать пароль и другие секреты из окружения процесса при запуске. В шаблонах оставлять только имена переменных с пустыми значениями. Не печатать развёрнутую конфигурацию с секретами в терминал или отчёты.

**Состояние:** исправлено в рабочем Compose: `SP_DB_PASSWORD` обязателен в окружении, значений секретов в конфигурации нет. Генерация, запуск и восстановление переменной из окружения существующего Docker-контейнера без печати проверены на стенде.

## 4. Размещение сертификатов не задаёт конфигурацию TLS

**Источник:** короткая инструкция, разделы 3.4, 3.5 и 3.7, шаг 3.

**Проблема:** документ монтирует каталог `certs` и публикует порты 443/8883, но не задаёт имена файлов, цепочку доверия, настройки включения TLS и доступ контейнерного пользователя к ключам. При этом финальная проверка допускает адрес HTTPS.

**Основание:** [ПРОВЕРЕНО по документу] В примере отсутствует конфигурация TLS ядра и UI; указано уточнить пути по спецификации релиза. Команда `chmod 600` применяется ко всем файлам каталога без проверки владельца и пользователя контейнера. [ВЫВОД] Одно монтирование каталога и публикация порта не подтверждают работу TLS.

**Исправление:** определить поддерживаемый образами способ настройки TLS, затем выпустить согласованные самоподписанные сертификаты для фактических адресов подключения. Передавать закрытые ключи согласно правилам проекта. Проверить доступ процесса к ключу, предъявляемый сертификат, HTTPS и MQTT TLS отдельно; фиксировать только реально выполненные проверки.

**Состояние:** исправлено и проверено для MQTT монолита: пользователь разрешил единственный файл ключа `/opt/smart-platform/certs/server.key` только на стенде. Создан самоподписанный сертификат, включён `MQTT_SSL_ENABLED`, заданы PEM-пути. Проверены TLSv1.3, доверие и IP сертификата, затем MQTT CONNECT с CONNACK0 на8883. UI запущен по HTTP8080 согласно новому Compose, отдельный TLS-терминатор не используется. Предоставленный Andromeda Root CA импортирован отдельно в Java truststore для исходящих соединений; он не является издателем самоподписанного MQTT-сертификата.

## 5. Процедуры инициализации в документах различаются

**Источник:** короткая инструкция, разделы 3.5–3.6; руководство, с.456–457, статья 74.

**Проблема:** короткая инструкция требует БД и схему `smart-platform`, ручное создание схемы и запуск ядра с `UPDATE=true`, `UPGRADE=true`. Руководство приводит БД `smartplatform` и отдельный инициализирующий контейнер, который после успеха завершается; штатный сервис назван `smart-platform`.

**Основание:** [ПРОВЕРЕНО по документам] Различия присутствуют в соответствующих разделах. Команды инициализации из руководства не доступны в извлечённом тексте PDF. [ВЫВОД] Эти процедуры нельзя объединять без подтверждения для конкретного релиза.

**Исправление:** определить поддерживаемую процедуру по поставке и фактическому entrypoint. На чистой БД проверить код завершения инициализации, структуру и системные ресурсы. Зафиксировать условия повторного запуска и штатные значения флагов. Не применять непроверенную инициализацию к БД с рабочими данными.

**Состояние:** по `start-sp-node.sh` подтверждены `INSTALL_SP`, `LOAD_DEMO`, `UPGRADE_SP` и `FROM_VERSION`; `UPDATE`/`UPGRADE` этим скриптом не читаются. На стенде по новому Compose согласованы БД/роль/схема `smartplatform`, схема создана init SQL PostgreSQL, до installer таблиц0. Одноразовый installer с `INSTALL_SP=true`, `LOAD_DEMO=true` завершился кодом0 и маркером успеха. Runtime не запускает установщик повторно. Обновление с прежнего релиза не проверялось.

## 6. В PDF отсутствует раскрытая конфигурация монолита

**Источник:** руководство, с.455, статья 74, шаг 1; с.465–468, статья 76.

**Проблема:** варианты Compose `In Memory` и `Kafka` на с.455 остались свёрнутыми. Руководство предлагает вставить конфигурацию, которой в PDF нет. Микросервисная глава содержит другие имена образов и скрипты развёртывания, но не заменяет отсутствующий монолитный Compose.

**Основание:** [ПРОВЕРЕНО] Отсутствие YAML на с.455 подтверждено рендерингом страницы. Среди URI-аннотаций с.455–458 ссылок на скачивание YAML не найдено. На с.465–468 описана отдельная архитектура с обязательной Kafka и архивом deployment, ссылка на который в проверенном разделе не найдена.

**Исправление:** получить полный Compose и установочные файлы именно поставляемого релиза. Сохранять исходные материалы отдельно от исправленной конфигурации. Не заменять монолитные образы кластерными по сходству имён или тегу `latest`.

**Состояние:** дефект PDF подтверждён. Позднее получен отдельный оригинальный монолитный Compose, по нему подготовлен и проверен вариант с `in-memory`, локальным JS и `caffeine`. Kafka/Redis и отдельные JS/MQTT-сервисы для этого состава не используются. Микросервисный вариант из PDF не проверялся.

## 7. Критерии готовности не подтверждают полную работоспособность

**Источник:** короткая инструкция, раздел 3.5, healthcheck ядра; раздел 3.7, шаги 2–3.

**Проблема:** проверка ядра зависит от наличия `curl` и ответа `/login`; документ ожидает `healthy` у всех трёх контейнеров, хотя healthcheck UI в Compose не задан. Финальная проверка ограничена открытием страницы входа.

**Основание:** [ПРОВЕРЕНО по документу] В Compose явно определены healthcheck только PostgreSQL и ядра. Healthcheck, который может быть унаследован из образа UI, и наличие `curl` в ядре не проверены. [ВЫВОД] Ответ страницы входа не подтверждает успешную авторизацию и обращение UI к API/БД.

**Исправление:** проверить утилиты и endpoints фактических образов; установить достижимые критерии готовности для каждого сервиса. Проверить отсутствие циклических перезапусков, доступность HTTP/HTTPS с рабочей станции, загрузку UI и успешную авторизацию с обращением к API. Отдельно фиксировать проверки транспорта, сохранности данных и восстановления после перезапуска, если они выполнялись.

**Состояние:** проверки адаптированы к фактическим образам: ядро — TCP-liveness, UI — Node HTTP с `Accept: text/html` (без него SPA отдаёт404). После исправления healthcheck запуск с ожиданием готовности завершился кодом0. Проверены форма входа в браузере рабочего компьютера, HTML/3 ресурса UI/API login+user, MQTT CONNECT на1883/8883, доверие TLS и повторный stop/up. Совпадение количества сущностей БД после перезапуска подтверждено; полная целостность данных и все функции платформы этим не доказаны.

## 8. Исправления предоставленного монолитного Compose

**Источник:** `input/images/docker-compose_monolith.yml`, отдельный номер версии отсутствует; SHA-256 указан в инвентаре поставки.

**Проблемы и исправления:**

- PostgreSQL создаёт роль `postgres`, а приложение подключается как `smartplatform` с `currentSchema=smartplatform`. В исправленной конфигурации PostgreSQL создаёт роль/БД `smartplatform`, init SQL — одноимённую схему. Проверено на новом томе, существующие данные не удалялись.
- UI указан как `/web-ui`; поставленный образ называется `/sp-web-ui:2.0.0`. Использовано фактическое имя и пользователь образа `node`.
- `mosquitto.conf` и truststore из `../infra/cacerts` отсутствуют. Добавлен конфиг Mosquitto, truststore собран из стандартных CA образа с добавлением предоставленного `input/ca.crt`.
- Настройки внешнего брокера не включают `MQTT_EXT_ENABLED`, по YAML defaultfalse. Включено явно; соединение `sp-monolith` подтверждено журналом Mosquitto.
- Значения паролей из оригинала заменены обязательным окружением; пароль truststore не передаётся аргументом JVM. Java JSSE подтвердил импортированный CA без такого параметра.
- Недоступный на стенде AI dispatcher выключен подтверждённой переменной `AI_DISPATCHER_ENABLED=false`. JMX и отладочные TRACE-настройки из образца не включены.
- Installer вывел Fontconfig `No writable cache directories`. В образе `HOME=/home/thingsboard`, а доступный сервису каталог — `/usr/share/smart-platform`; задан `XDG_CACHE_HOME=/usr/share/smart-platform/.cache`, `fc-cache -f` с ним завершился без ошибок.

**Состояние:** исправленный [Compose](../../deploy/compose/monolith.yml) прошёл проверку конфигурации и фактическую установку/запуск на стенде; результаты и границы приведены в [инструкции](../installation/smart-platform-2.0.0.md).
