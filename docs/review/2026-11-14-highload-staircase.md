# Ступенчатый highload: остановка при 65% CPU

14 ноября 2026 года на [установочном стенде](../../inventory/hosts/stand/README.md)
проверены ступени 30×150 и 40×200 с периодом сигналов 1000 мс.
На 40×200 десятисекундный CPU всей Ubuntu достиг **65,23%**; в
**23:56:46,442 по Москве / 20:56:46,442 UTC** серия остановлена по
согласованному условию. Следующие ступени не запускались.

## Окружение и условия

- Ubuntu 26.04.1 LTS, x86_64, 4 CPU, 14,89 GiB RAM, около 4 GiB swap.
  Docker CLI 29.1.3, служба Docker active. Поставка платформы 2.0.0 указана
  по карточке; Image ID и состояние каждого runtime-контейнера Ubuntu
  повторно не проверялись.
- На Mac: macOS 26.5.2, Docker Engine 28.5.1, Compose v2.40.3-desktop.1.
  Использован только локальный Compose-проект `sp-highload-mac`. Платформа
  не перезапускалась, её конфигурация не менялась. На время работы включено
  удержание Mac от сна через `caffeinate`.
- SSH alias `irobo` подтвердил неинтерактивный доступ к выбранному стенду.
  Ресурсы читались через `/proc/stat`, `/proc/meminfo` и `statvfs` каждые
  10 секунд. CPU нормирован на все ядра, iowait записан отдельно; RAM —
  `100 × (MemTotal − MemAvailable) / MemTotal`.
- Остановка — первое CPU или RAM ≥65%, потеря контроля либо ошибка доставки.
  Лимит ступени — 600 секунд от команды запуска. Плановая остановка
  запрашивается за 10 секунд до лимита, оставляя резерв на Docker.
- Архив highload совпал с SHA-256 инвентаря. Сценарии проверены независимым
  разбором XLSX. Поставочный шаблон не изменён; конфигурация Agent сохраняет
  `total_topic=5000`, апертуру и пакетную отправку.

## Результаты

Длительность в таблице включает запуск и подтверждение остановки. CPU/RAM —
статистика имеющихся десятисекундных замеров; первый интервал ступени может
частично включать предыдущий режим. p95 вычислен методом ближайшего ранга.

| Ступень | Задано публикаций/с | Длительность, с | Замеры | CPU среднее / p95 / max, % | RAM среднее / max, % | Результат |
| --- | ---: | ---: | ---: | --- | --- | --- |
| 30×150 | 4500 | 590,391 | 59 | 36,42 / 41,01 / 44,60 | 17,36 / 17,45 | Плановый лимит, 4500/4500 свежих ключей |
| 40×200 | 8000 | 108,087 | 11 | 57,49 / 65,23 / 65,23 | 17,46 / 17,52 | CPU ≥65%, 8000/8000 свежих ключей |

Оба интервала короче 600 секунд. Фактическая работа PubMQTT на 40×200 по
Docker — 105,947 секунды. Swap во всех замерах — 0. Доступное место на
разделе платформы уменьшилось с 77,71 до 76,67 GiB; это изменение всей
файловой системы, а не отдельное измерение размера БД.

API с ролью TENANT_ADMIN подтвердил полное покрытие через 12,214 секунды
на 30×150 и 12,165 секунды на 40×200. После этого все завершённые снимки
показывали полный набор ключей; временные метки saw-сигналов каждого
устройства продвигались. На 30×150 отдельно сравнили два снимка всех
4500 сигналов с интервалом 10,823 секунды: продвинулись все 4500 временных
меток, максимальный возраст последних точек — 2,924 секунды.

Пороговая запись получена на Mac в 23:56:46,385981. Запрос stop отправлен
через 50,580 мс, остановка PubMQTT подтверждена через 296,495 мс от получения.
Для этих задержек использованы часы Mac, поскольку часы стенда немного
смещены относительно них. Полная остановка highload завершилась в
23:56:47,274 по Москве. Финальный снимок Docker: все три контейнера
остановлены, OOMKilled=false, RestartCount=0. Код 137 PubMQTT соответствует
предусмотренному `docker stop --time 0`; Agent и Mosquitto завершились с 0.

После остановки, в 23:59:27: CPU 3,03%, RAM 17,42%, swap 0; HTTP `/` — 200,
API авторизации доступен. В платформе осталось 40 тестовых устройств,
50 устройств всего. Устройства и накопленная телеметрия не удалялись.

## Границы проверки и материалы

8000 публикаций/с — настройка PubMQTT, а не измеренная скорость записи в БД.
Опрос API добавляет нагрузку и входит в наблюдаемые CPU/RAM. На 40×200
подтверждены свежие данные всех ключей после старта и живость контрольных
сигналов всех устройств; отдельной проверки продвижения каждого из 8000
ключей между двумя снимками не было. Успешное покрытие при
`total_topic=5000` относится к этому запуску и не проверяет все режимы буфера.

Короткая ступень 40×200 не устанавливает устойчивую промышленную
производительность. Ступени 50×250 и выше, скорость записи БД, просмотр
дашбордов под нагрузкой, перезагрузка, сон Mac и живые отказы не проверялись.
Ошибки управления и накопленные SSH-замеры покрыты отдельными unit-тестами;
имитации не заменяют проверку реального отказа.

Процедура — [highload с SSH-контролем](../installation/highload-mac.md#ступенчатый-тест-с-контролем-через-ssh).
Локальные отчёт с графиком, средние/p95/max, временные ряды ресурсов,
счётчики доставки и финальные проверки сохранены в
`reports/stand-192.168.10.107/20261114T204435Z-highload/` и исключены из Git.
Значения телеметрии, токены и пароли в них не сохранялись.

Для применения результата при подборе промышленной нагрузки требуется
отдельно проверить длительную работу выбранного профиля, скорость записи
и потери/задержки каждого типа сигнала.
